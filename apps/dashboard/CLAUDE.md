# CLAUDE.md: apps/dashboard

This file covers the dashboard app only. Product context and the domain are in the root `CLAUDE.md`.

## Stack

- **Nuxt 4** (source lives in `app/`, Nuxt 4 layout), **Nuxt UI v4**, Tailwind CSS v4, TypeScript.
- Icons: Iconify **lucide** (`i-lucide-*`) and **simple-icons**, both installed locally.
- Scaffolded from the official `ui` starter template, with its marketing content removed.

## Commands

Run from `apps/dashboard/`, or from the root with `pnpm --filter dashboard <script>`:

```bash
pnpm dev          # http://localhost:3010 (3000 is used by other local projects)
pnpm build        # production build in .output/
pnpm preview
pnpm lint         # ESLint (add --fix)
pnpm typecheck    # vue-tsc through nuxt typecheck
pnpm test:e2e     # Playwright; needs `docker compose up -d db` (root). Builds and starts its own servers
pnpm test:e2e e2e/sign-in.spec.ts             # one file
pnpm test:e2e --project phone -g "signs in"   # one project, tests whose name matches
pnpm test:unit    # Vitest, for pure modules (app/utils/format.ts, the Order form helpers in app/utils/orders.ts, the Statement labels in app/utils/balance.ts, the Payment form in app/utils/payments.ts, the Delivery note issuer in app/utils/business.ts)
```

First run on a machine: `pnpm exec playwright install chromium` (both projects use Chromium).

### Environment

`nuxt.config.ts` loads the root `.env`. Public runtime config, overridable at run time with `NUXT_PUBLIC_*`:

| Key | Env at run time | Default |
|---|---|---|
| `apiBase` | `NUXT_PUBLIC_API_BASE` | `http://localhost:${API_PORT}` (3001) |
| `supabaseUrl`, `supabasePublishableKey` | `NUXT_PUBLIC_SUPABASE_URL`, `NUXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` from `.env` at build time |
| `authMode` | `NUXT_PUBLIC_AUTH_MODE` | `supabase`. `test` is for E2E only (see below) |

The app is a client-side SPA (`ssr: false`): everything is behind sign-in and all data comes from the API with a bearer token held in the browser.

## Tests

- **Seam: the running app, end to end.** Playwright (`playwright.config.ts`, tests in `e2e/`) starts the API (`API_AUTH_VERIFIER=test`) on **3101** and a production build of the dashboard (`NUXT_PUBLIC_AUTH_MODE=test`) on **3110**, never the dev ports 3001/3010. The build goes to `.nuxt-e2e`/`.output-e2e` (`POLLUX_E2E=1`), so it never clobbers `pnpm dev`. Locally, servers already running on those ports are reused.
- **Its own database:** global setup drops and recreates **`pollux_e2e`** on the docker-compose Postgres (`E2E_DATABASE_URL` to override; it must be local and its name must contain `e2e`), then applies `db/migrations`. Never `pollux_test`: the API suite drops that one on every run.
- **Projects:** `phone` (Pixel 7, the default way the app is used) runs every test; `desktop` runs only tests tagged `{ tag: '@desktop' }` (flows that must also work at the PC, like the phone-order flow). Use the `openSidebar` fixture, since on a phone the sidebar is a drawer.
- **Test sign-in mode:** with `NUXT_PUBLIC_AUTH_MODE=test` the dashboard skips Supabase and the **password is the bearer token**, which the API's test verifier reads as a user id (the API refuses that verifier in production). The login page shows a "Modo de prueba" notice.
- **Fixtures** (`e2e/fixtures.ts`): `createOwner(...businessNames)` inserts a user and their businesses straight into the DB (no onboarding endpoint exists); `signIn(userId)` goes through `/login`; `createCustomer(userId, input)` posts a Customer to the API in the user's first business, and `callApi(userId, method, path, body?)` makes any other API call as the user (e.g. Products with stock, or Orders), for tests that only need that data as a starting point. The flow under test goes through the UI. Each test makes its own user and businesses, so tests run in parallel.
- Locate by role, label and Spanish text, never CSS classes. Toast titles also appear in a hidden live region, so match them with `{ exact: true }`. `UTable` adds an empty decoration row to its header, so count data rows with `dataRows(table)` from `e2e/catalog.ts`, which also has `createCategory` and `createProduct` for tests that start from a catalog.
- `test/` holds Vitest unit tests for pure modules only; it runs in a far-west time zone so a date that drifts through UTC fails.

## Structure and conventions

- **App shell:** `app/layouts/default.vue` wraps every page in `UDashboardGroup` with a collapsible `UDashboardSidebar` and `UNavigationMenu`. **Each page renders one `UDashboardPanel`** with a `UDashboardNavbar` in `#header` and its content in `#body`. To add a section, create the page and add it to the `links` array in the layout.
- **Routes and UI text are in Spanish** (`/pedidos`, `/clientes`, `/cuentas-corrientes`, `/productos`). `app.vue` passes Nuxt UI's `es` locale to `<UApp>` and sets `lang="es-AR"`. Page titles are set with `useSeoMeta({ title })` and the template appends `· Pollux`.
- **Auth and business:** `useAuth()` (Supabase session or test mode, restored by `plugins/auth.ts`), `middleware/auth.global.ts` (signed-out users go to `/login?redirect=<path>`; the first navigation loads the user's businesses from `GET /me` and sends users with several and no choice on this device to `/negocio`), `useActiveBusiness()` (the business list and the active one, remembered per device and per user in `localStorage`; `GET /me` is sent without `X-Business-Id`, so a stale choice just means picking again), `useSignOut()` (`endSession()` is the one sign-out sequence, also used on a 401). `/login` and `/negocio` use no layout. The sidebar shows `BusinessSwitcher` only for users with several businesses.
- **Formatting** (`app/utils/format.ts`, auto-imported): `formatMoney("12345.50")` → `$ 12.345,50` (the decimal string goes straight to `Intl`, never through a float), `formatDate` (`yyyy-mm-dd` → `dd/mm/yyyy` as text, timestamps in Argentina time), `maskCuit` while typing, `formatUnits(1200)` → `1.200` and `formatUnitsChange(-3)` → `-3` / `+24` for stock quantities, `todayInArgentina()` (today as `yyyy-mm-dd` in Argentina, for date inputs), and `<enum>Labels` with the Spanish name of every enum value. Show values only through these.
- **Clientes** (`pages/clientes/`): list with search and town filter kept in the URL (`?q=`, `?localidad=`, `?pagina=`), `nuevo` (name plus one Branch), and `[id]` (the Balance up front via `CustomerBalanceFigure` with "Registrar pago", "Ver resumen de cuenta" and "Más acciones" ("Saldo inicial" while there is none, "Ajustar saldo"), the 5 latest Orders with "Ver todos" to `/pedidos?cliente=`, the 5 latest Payments, details, Branches, tap-to-call). `utils/customers.ts` holds the `Customer`/`Branch` types (inferred from the API) and the form states; `components/customer/` holds the shared fields and the edit modals (`CustomerEditModal`, `CustomerBranchFormModal`). Forms validate with the `@pollux/contracts` schemas the API uses.
- **Cuentas corrientes** (`pages/cuentas-corrientes/`, `utils/balance.ts`, `components/balance/`): `index` lists the Customers whose Balance isn't zero as the API sorts them (largest first, credits last; `?pagina=`, 50 a page), each as "Debe $ …" or "A favor $ …" (`balanceAmountText`) linking to the Statement, with a "Registrar pago de <cliente>" button that opens `PaymentSheet` for that row's Customer (no picker needed), under the "Saldo total" (`balanceTotal`, net of credits, and said so on screen). `BalanceEntryModal` is the one form for manual entries: `kind: 'opening'` is "Saldo inicial" ("Debe"/"A favor", amount, date) and `kind: 'adjustment'` is "Ajustar saldo" ("Sumar al saldo"/"Restar del saldo", amount, the required "Motivo", date); the amount is typed without a sign (`signedBalanceAmount`), the resulting Balance shows while typing (`balanceAfter`), and the date defaults to today and refuses a future day in the form (`pastDaySchema`; #62 switches to the shared schemas once #59 lands). Both the Customer page and the Statement offer them under "Más acciones" (`useBalanceEntryActions`), "Saldo inicial" only while the Customer has none (the page's Balance, `GET /customers/:id/balance`, says so in `hasOpeningBalance`; refreshing it after saving hides the action). `[clienteId]/imprimir` is the Statement's print view ("Imprimir resumen" in the Statement's "Más acciones", carrying `?desde=`/`?hasta=`): no layout, forced light (`colorMode: 'light'` page meta), the business, Customer and period, a "Saldo anterior" row when the range has a start, a Fecha/Concepto/Debe/Haber/Saldo table of the whole range (pages of 200), and the "Saldo final", also for a range with no entries (the last entry up to `?hasta=`, or the current Balance); it calls `window.print()` once loaded and again from "Imprimir" (hidden in print with `print:hidden`). The only print CSS is `@page` (A4) in `main.css`, shared with the Delivery note; a phone saves or shares it as PDF from the print dialog. `[clienteId]/index` is the Statement: "Registrar pago" in the navbar, the current Balance (`CustomerBalanceFigure`: big amount with "Debe", "A favor del cliente" or "Al día", never color alone), a "Desde"/"Hasta" range kept in the URL (`?desde=`, `?hasta=`, `?pagina=`; a backwards range asks nothing), and the entries oldest first, 50 a page, each with its label (`statementEntryLabel`: "Entrega pedido N° 12", "Pago en efectivo", "Ajuste: motivo", …), its date, "Debe"/"Haber" (`statementAmountText`) and the running "Saldo", which counts entries before the range too.
- **Inicio** (`pages/index.vue`): the two everyday actions first, "Nuevo pedido" (to `/pedidos/nuevo`) and "Registrar pago" (`PaymentSheet` with no Customer, so it asks for one), then "Stock a reponer" (only when `GET /stock/shortages` lists something; its 50 largest shortfalls): each short Product linking to `/productos/:id` with its Code, the `OrderStockWarning`, and the Pending Orders that reserve it (`N° 12 · Customer · Delivery date · units`) linking to `/pedidos/:id`, then today's Orders still to deliver (Pending, Delivery date today in Argentina; count and total, one page of 200) with "Ver reparto", and the "Saldo total" from `GET /customers/with-balance` (net of credits) with "Ver cuentas corrientes". Recording a Payment refreshes the total.
- **Theme:** `app.config.ts` sets `primary: green` and `neutral: slate`, and `assets/css/main.css` overrides the green scale. The Nuxt UI ESLint rules block raw Tailwind palette colors (`no-palette-colors`), so use semantic tokens (`text-primary`, `text-muted`, `bg-elevated`, `border-default`, …) instead of `text-green-500`.
- **Productos** (`pages/productos/`): the catalog (search, Category filter and "Mostrar inactivos" kept in the URL as `?q=`, `?categoria=`, `?inactivos=1`, `?pagina=`; Active only by default), `nuevo`, `[id]` (details, Active switch, "Cambiar precio", price history), `categorias` (create and rename; each Category opens the catalog filtered by it) and `actualizar-precios` (the Category Price update, reached from `categorias` with `?categoria=`: pick "Aumento" or "Rebaja" and a percent without a sign, preview old vs. new Prices, then apply the previewed Category and percent; editing the form after the preview discards it, and the form is locked while applying). The edit form leaves the Price out: a Price changes only through "Cambiar precio", so every change is a deliberate entry in the history. `utils/products.ts` holds the `Product`/`Category`/`PriceChange` types and the form schemas, built on the `@pollux/contracts` ones but accepting a Price typed the es-AR way (`1.234,50`, read by `parseDecimalInput` in `utils/format.ts`). The Category picker offers "Sin categoría" as an item whose value is `null`, which the API reads as "clear it" (a missing field would mean "no change"). `useCategories()` shares the Category list under the `categorias` key. `formatPercent("10.50")` → `10,5 %` shows VAT rates.
- **Stock** (on the Product, plus `utils/stock.ts`): the catalog and `[id]` show On-hand, Reserved and Available stock as "Físico", "Reservado" and "Disponible"; a negative Available is red, with a warning icon (catalog) or a sentence (detail), never color alone (`ProductStockFigures`). `[id]` has "Ajustar stock" (`ProductStockAdjustmentModal`: "Sumar"/"Restar" plus a quantity without a sign, since a phone's numeric keypad has none, then a reason and notes; it shows the resulting On-hand while typing) and lists the Stock movements newest first with their cause (`movementCause`), 20 at a time with "Ver más". `conteo-inicial` (from the catalog's navbar) loads the whole Active catalog in pages of 200, filters it on the device so counts typed in hidden rows survive, and sends only the typed counts in one `POST /stock/initial-count`; the save button sits in the panel's `#footer` so it stays in reach. Counts are typed as whole units, `1.200` allowed (`unitsInputSchema`).
- **Pedidos** (`pages/pedidos/`): the list (filters by Customer, town, status and Delivery date kept in the URL as `?cliente=` (an id), `?localidad=`, `?estado=`, `?fecha=`, `?pagina=`), `nuevo`, `[id]/index` (lines, Discounts, totals, status; "Editar" and "Cancelar pedido" with a confirm modal while Pending) and `[id]/editar`. New and edit share `OrderForm`, which renders the whole panel: Customer (`CustomerSearchMenu`, searched by the API; fixed on edit), Branch (shown as text when the Customer has one, a select otherwise), Delivery date (a native date input, tomorrow in Argentina by default via `tomorrowInArgentina`), lines with quantity steppers and a Discount each, `OrderProductPicker` (search or Category, with Price and Available stock; beside the lines from `lg`; tapping a result adds one unit. "Buscar producto" is a combobox for phone orders at the PC: the arrow keys move through the results, Enter adds the highlighted one (the first by default, waiting for the typed search's results if they haven't arrived) and never submits the Order, and the text stays selected, also after a click, so Enter adds one more and typing starts the next search; on a touch screen (`pointer: coarse`) the keyboard's search key only searches and closes the keyboard), the Order Discount and notes, and a `#footer` with the live total and Save. Save ignores a second tap while the first is in flight. The live total uses `orderTotals` from `@pollux/contracts` through `orderFormTotals` (`utils/orders.ts`); a Discount still being typed counts as none. A line warns "Sin stock suficiente" when it would leave Available stock negative (from the picked Product's Available stock; `editar` loads each kept line's Product for it, and counts what the Order already reserved). `OrderStockWarning` is the one wording for it (icon and text, the Available stock and the units missing; `projected` for the form's "quedaría en"), also on `[id]/index`, which loads a Pending Order's Products (`GET /products/:id`) and marks each line whose Product has negative Available stock (none for Delivered or Cancelled Orders), and on Inicio. After saving, the API's `warnings` are listed (the saved-Order sheet, or a toast after an edit); neither blocks. On edit, kept lines show their frozen `unitPrice` as "precio del pedido" and new lines the current Price as "precio actual", which the API freezes on save. Order numbers show as `N° 12`. `[id]/index` puts "Entregar" first while Pending and "Deshacer entrega" (a confirm modal that says Payments are not voided) once Delivered. `[id]/remito` is the Delivery note's print view ("Imprimir remito", or "Reimprimir remito" once it has a number, on `[id]/index`; hidden for a Cancelled Order that never had one): opening it calls `POST /orders/:id/delivery-note`, which takes the next number the first time only, so a reprint shows the same number. Same pattern as the Statement's print view: no layout, forced light, the business as issuer (`issuerLines` in `utils/business.ts`: the razón social or else the name, then Domicilio, Teléfono, CUIT, Condición frente al IVA, Ingresos Brutos and Inicio de actividades, each only when filled), "Remito N°", the issue date and Order number, the Customer (CUIT, VAT condition) and Branch, the Delivered date (or the Delivery date), a Cant./Producto/Precio/Desc./Subtotal table, the Order Discount and total, a signature line and "Documento no válido como factura"; it calls `window.print()` once loaded and again from "Imprimir".
- **Entregar, Registrar pago and reparto** (`components/payment/`, `utils/payments.ts`): `PaymentSheet` is the one bottom-sheet `UDrawer` where money changes hands. With an `order` it is Entregar (from the Order page or the reparto list): the total, "Pago" (a radio group: "Cuenta corriente (sin pago)", pre-selected, then Efectivo, Transferencia, Cheque and Otro), and for a Payment method the "Importe" (starting at the total, typed the es-AR way) and an optional "Referencia"; then the Delivered date and "Confirmar entrega", a single `POST /orders/:id/deliver` with the optional `payment`. With a `customer` and no Order it is Registrar pago (Customer page, Statement, Cuentas corrientes rows); with neither (Inicio) it is Registrar pago with a required "Cliente" picker (`CustomerSearchMenu`) first. Then the method (Efectivo by default), Importe, Referencia and "Fecha de pago" (`POST /payments`). Both dates default to today in Argentina and refuse a future day in the form itself (`paymentFormSchema(delivering)`, which reuses `deliveredOn` from `orderDeliverSchema` and `paidOn` from `paymentCreateSchema` in `@pollux/contracts`, the API's own rule and Spanish messages). A second tap in flight is ignored, and API validation errors come back as a toast, since the API names the delivery's fields `payment.amount`. Success shows "Pedido entregado" or "Pago registrado" with the Payment in words ("Pago en efectivo de $ 1.000,50") and the Customer's new Balance (`GET /customers/:id/balance`), and emits the delivered Order or the Payment. `PaymentList` shows Payments (method, date, reference, amount, optionally the Order) with "Anular pago", which opens `PaymentVoidModal` (the reason is required; the modal is the confirmation); a voided Payment stays listed with "Anulado", its reason and the amount struck through. The Order page lists its Payments under "Pagos"; the Customer page has "Registrar pago" beside the Balance and the 5 latest Payments under "Pagos recientes" (`GET /payments?customerId=`). `/pedidos/reparto` (the "Reparto" button on the list) shows one day's Orders (`?fecha=`, today by default; one page of 200) grouped by town, each group with its count and total, cancelled Orders left out, and "Entregar" on each Pending row; the delivered Order replaces its row in place.
- **Compras y Proveedores** (`pages/compras/`, `pages/proveedores/`, `utils/purchases.ts`): `/proveedores` lists Suppliers (search by name or CUIT in `?q=`) and creates or edits them in `SupplierFormModal` (tap a row to edit; an edit sends every field, so a blank one is cleared). `useSuppliers()` shares the whole Supplier list (one page of 200) under the `proveedores-todos` key for pickers. `/compras` lists Purchases latest first, filtered by Supplier and a date range kept in the URL (`?proveedor=` (an id), `?desde=`, `?hasta=`, `?pagina=`). `/compras/nueva` takes a Supplier, the Purchase date (today by default), an optional invoice number, notes and lines: "Agregar producto" searches the API (Inactive Products included, since they may still be bought) and each pick adds a line with its quantity (whole units) and unit cost (typed the es-AR way), with a live total in the panel's `#footer`. Save ignores a second tap while the first is in flight (in the Supplier modal too). Saving goes to `/compras/:id`, the read-only detail; Purchases can't be edited or deleted.
- **Nuxt UI first.** Build screens from Nuxt UI components (forms, tables, menus, overlays, steppers, dashboard parts, …) and their props, slots and variants. Before writing a custom component, look for one in Nuxt UI (Nuxt UI MCP or `nuxt-ui` skill). Write a custom component only when nothing fits, and compose it from Nuxt UI parts.
- **List filters in the URL:** `useListQuery({ search: 'q', filters: { town: textParam('localidad') } })` holds a paged list's state in `route.query`: a debounced search (`search` for `v-model`, `searched` for the request), one ref per filter in `filters` (`textParam`, `flagParam`, `dayParam` (only a whole `yyyy-mm-dd` counts), `enumParam`) with `values` holding what each sends, `page` (`?pagina=`), `paging` (`limit`/`offset`, 50 a page) and `sources` for `useAsyncData`'s `watch`. A search or filter change goes back to page 1. Every paged list uses it; a new filter kind is a new `UrlParam`.
- **Form submit:** `const { saving, onSubmit } = useFormSubmit<Output>(form, async (data, request) => { … })` for `<UForm @submit="onSubmit">` and the submit button's `:loading="saving"`. It ignores a submit while one is in flight, its `request` puts the API's field errors on `form` (pass `null` as the form when the API names the fields differently, so they come as a toast, as in `PaymentSheet` and `conteo-inicial`), and an `ApiRequestError` just ends the submit. Catch one inside the action only to react to a code, then rethrow. Every form that saves through the API uses it.
- **Form validation:** every `UForm` validates a field as it's typed in (`validateOn: ['input']`), never on blur or change. `app.vue` sets that once for the whole app through `<UTheme :props>`, modals and drawers included, so don't pass `validate-on` per form. The reason: tapping the submit button blurs the field first, and an error appearing or clearing right then moves the button out from under the finger, so the tap is lost (#41). Nuxt UI starts validating a text field as you type only once it has been left once, so an error shown by a submit on an untouched field stays until the next submit. Number inputs, selects, radios and switches validate on every change.
- **Lists:** `UPageList divide` draws each divider with an absolute `::after`, so its children need `relative` (`UPageCard` has it; a plain `ULink` row doesn't). For a tappable row, use a `ULink` holding the visible text: a `UPageCard` link is an empty overlay that Playwright sees as hidden.
- **Minimal CSS, customized globally.** Write as little CSS as possible. Change the look at the app level: theme colors and component defaults or slot classes in `app.config.ts` (`ui: { button: { … } }`), and design tokens in `assets/css/main.css` (`@theme` and CSS variables). Don't restyle individual component instances with long `class` or `:ui` overrides or scoped `<style>` blocks. Use Tailwind utility classes for layout (flex, grid, spacing). Override a single instance only when a screen truly needs something different from the rest of the app.
- **Where to look, in order:** (1) Nuxt UI (the `nuxt-ui` skill and the Nuxt UI MCP) for components, theming and app config; (2) Nuxt (the Nuxt MCP) for routing, data fetching, middleware and config; (3) the `modern-web-guidance` skill for web-platform practice that neither covers: accessibility, forms and autofill, dates and timezones, print CSS, performance (LCP, INP, CLS), security and client-side JS APIs. Modern Web Guidance never overrides "Nuxt UI first": use it to get the platform details right inside or around Nuxt UI components, not to hand-roll a component Nuxt UI already provides.
- **ESLint style:** no trailing commas, 1TBS braces. `pnpm lint --fix` handles most of it.
- **Mobile-first:** the sidebar turns into a drawer on small screens (`v-model:open`). Check every new screen at phone width, since order entry and payments happen on the road.

## Data access

The dashboard **only talks to `apps/api`**. Don't add Nuxt server routes holding business logic, and don't query Postgres or Supabase tables from here. Supabase Auth on the client (sign-in and session, in `useAuth`) is the one exception.

- **`useApi()`** wraps Hono's typed client (`hc<AppType>`, typed from `api/src/app` through a type-only workspace dev dependency) and adds the bearer token and `X-Business-Id` to every request. Call it in setup, then `const data = await request(c => c.me.$get())`: it returns the typed body of the success response, or handles the error and throws `ApiRequestError`. To name a response type, use `InferResponseType<ApiClient['customers'][':id']['$get'], 200>` (`ApiClient` is exported from `useApi.ts`).
- **Errors** arrive as `{ error: { code, message, details? } }` with a Spanish message. `request` maps them: 401 signs out and goes to `/login` (coming back afterwards); 403 and 400 `business_not_selected` go to the business picker; 400 `validation_error` puts `details` on a form's fields when you pass `{ form }` (a `UForm` ref); anything else becomes a toast. Callers only catch `ApiRequestError` to stop their own flow.
- Route middleware passes `{ navigate: false, returnTo: to.fullPath }` and returns `navigateTo(error.redirectTo)` itself, since it can't start a second navigation and the current page isn't the one being entered.
