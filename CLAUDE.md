# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

**pollux-core** is a proof of concept for a management app for small and medium businesses in Argentina (PyMEs). The DB schema is written and applied to Supabase, with Gio Pack demo data seeded. The dashboard has its foundation (sign-in, the typed API client, the business switcher, formatting, Playwright) and the sections of spec #2 built on it (Inicio, Pedidos, Clientes, Cuentas corrientes, Productos, Compras, Proveedores); the remaining dashboard tickets refine them. The API is scaffolded (app factory, Supabase auth and business selection, `GET /me`, test harness); the business modules come next.

The work is planned in two specs on GitHub: **#1 (API)** and **#2 (dashboard)**. Each is split into ticket sub-issues labelled `api` or `dashboard`, linked by native blocked-by relationships. The API is built first. See **Working on tickets** below.

Each part has its own `CLAUDE.md` with its stack, commands and conventions: `apps/api/`, `apps/dashboard/`, `db/`. Keep details there; this file covers only what applies across the whole repo.

## Repository layout

This is a **pnpm workspace** (`pnpm-workspace.yaml`: `apps/*`, `packages/*`, `db`). pnpm build-script approvals (`allowBuilds`) live in the root `pnpm-workspace.yaml`, not in the individual apps.

```
apps/api/         Hono API: business logic and the only thing that talks to the DB
apps/dashboard/   Nuxt 4 + Nuxt UI v4 frontend; calls apps/api and never touches the DB directly
packages/         Shared workspace packages. `@pollux/contracts`: enum values, CUIT validator, money helpers and the Zod schemas both apps use
db/              The @pollux/db package: Drizzle schema (src/schema/) and drizzle-kit config
db/migrations/    SQL schema migrations generated by drizzle-kit, applied in order
db/seeds/         Dev and demo data (e.g. a Gio Pack-like catalog and customers)
docker/           Dockerfiles and local-env support files (e.g. api.Dockerfile, dashboard.Dockerfile)
docs/             Product and architecture docs (domain notes, ADRs)
docker-compose.yml  Local Postgres 17 (port 5433) for the API test suite; `api` and `dashboard` are commented placeholders
.env.example      Env vars shared by compose and the apps; copy to `.env`
```

The schema belongs in `db/`, not inside `apps/api`, so it stays independent of the API framework and of the DB host.

## Stack (decided)

- **Frontend:** Nuxt 4 with **Nuxt UI v4**. Use Nuxt UI components before writing custom ones. See `apps/dashboard/CLAUDE.md`.
- **Backend:** a separate Node API. See `apps/api/CLAUDE.md`.
- **Database:** a **remote Supabase project** (Postgres 17 plus Supabase Auth), used for all of development. The only local Postgres is the docker-compose one, used by the API tests. **Multi-tenant**: many businesses share the database, and Gio Pack is the first. The schema must stay portable to self-hosted Postgres. See `db/CLAUDE.md`.

## Still open (don't treat these as decided)

- A possible move to self-hosted Postgres, and whether Supabase Auth stays. Neither is planned yet.
- Infrastructure and deployment. Vercel's free tier is being considered for the POC, so avoid designs that need long-running processes, background workers or persistent local disk unless asked.

## Domain context

The reference customer is **Gio Pack**, a distributor in Corral de Bustos, Córdoba. Users and data are in Spanish (es-AR), so the UI must be in Spanish. Use Argentine conventions: ARS currency, `dd/mm/yyyy` dates, CUIT for tax IDs.

### How the business works
- **Route-based selling:** each day the owner visits a different town to take orders (preventa). The next day they go back to deliver (reparto). So orders are tied to a town or route and a delivery date.
- Some orders come in **by phone**, and these must go through the same order flow.
- **One price list for everyone.** Large orders sometimes get a discount, so discounts apply to the **order** (or its line items), not to the customer.

### What the current system does and why it fails
Their current desktop-only system is used only for stock, purchase invoices, price updates and **remitos** (delivery notes). Everything else lives in Excel. Their main complaint:

> The system makes me register each customer differently depending on whether they're on cuenta corriente or pay cash. I never know how they'll pay until I drop off the order.

**Core design rule:** the **payment method is decided per delivery or payment, not per customer.** There is one customer entity. Any customer can pay cash on one delivery and put the next one on account. A customer may have a *default* payment method or credit flag, but it must never split customers into different types or tables.

### Features in scope
1. **Order entry** (in the field and by phone) that **updates stock automatically** (reserve or decrement).
2. **Remitos** generated from orders or deliveries (the one thing the current system does well).
3. **Customer ledger** (debe/haber, cuenta corriente): sales add debits, payments add credits, the balance is derived. This replaces the Excel sheet.
4. **Mixed payment handling:** cash, account, or other methods, chosen when the order is delivered or paid.
5. **Digital product catalog.**
6. Products, stock, purchases (boletas de compra) and price updates, at parity with the current system.

Invoicing (facturación) is done today through the **ARCA** portal (formerly AFIP) and is **out of scope for now**. Don't build ARCA/AFIP integration unless asked, but keep the sales model compatible with adding electronic invoices later.

### UX constraints
- The current tool is "only usable from the PC," which is a main pain point. **Mobile-first:** order entry and payment recording must work well on a phone, on the road.
- The user dropped the old system because it was cumbersome. Keep common flows (take an order, record a payment, check a customer's balance) to as few steps as possible.

## Commands

Versions are pinned: **Node 24.22.3** (`.nvmrc`, so `nvm use` picks it up) and **pnpm 12.21.0** (`packageManager` and `engines` in the root `package.json`). `engineStrict` in `pnpm-workspace.yaml` makes `pnpm install` fail on any other version.

```bash
pnpm install                        # from the root, installs every workspace
pnpm dev:api                        # API on http://localhost:3001 (API_PORT); see apps/api/CLAUDE.md
pnpm test:api                       # API tests; needs `docker compose up -d db`
pnpm dev:dashboard                  # Nuxt dev server on http://localhost:3010
pnpm build:dashboard
pnpm --filter dashboard lint        # or typecheck; see apps/dashboard/CLAUDE.md
pnpm --filter dashboard test:e2e    # Playwright E2E on ports 3101/3110 and DB pollux_e2e; needs `docker compose up -d db`
pnpm db:generate --name <change>    # new SQL migration from schema changes; see db/CLAUDE.md
pnpm db:migrate                     # apply pending migrations to Supabase
pnpm db:seed                        # idempotent Gio Pack demo data; links TEST_USER as owner
```

Copy `.env.example` to `.env` and fill in the Supabase values. The dev DB is remote, so development needs nothing running locally.

`docker-compose.yml` has a local Postgres (port 5433) that **the test suites use** (`docker compose up -d db`): the API tests recreate a `pollux_test` database there and the dashboard's Playwright run recreates `pollux_e2e`; neither touches Supabase. Development still runs against Supabase. The dashboard uses port 3010 because 3000 is taken by other local projects.

## Deployment (Vercel, POC)

`vercel.json` deploys one Vercel project with two **services**: `dashboard` (Nuxt, public at `/`) and `api` (Hono, public at `/api`). Vercel passes the path through unchanged, so the API serves its routes under `/api` itself (`apps/api/src/index.ts`), and a dashboard built on Vercel calls `/api` on its own origin (no CORS needed). No service calls another server-side, so there are no bindings. Project env vars: `DATABASE_URL` (the session pooler, port 5432; the API doesn't use the transaction pooler, see `apps/api/CLAUDE.md`), `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` (read by the dashboard at build time) and `ENABLE_EXPERIMENTAL_COREPACK=1` (so Vercel uses the pinned pnpm). Installs pass `--config.engine-strict=false`, since Vercel's Node 24 patch may not be the pinned one.

## Working on tickets

- **Pick from the frontier.** Take an open ticket labelled `ready-for-agent` whose blockers are all closed. Read the ticket and its parent spec (#1 or #2) before starting; the spec holds the decisions the ticket depends on.
- **One ticket, one branch, one PR.** Branch from up-to-date `main` (e.g. `api/3-foundation`, `dashboard/14-foundation`). Open a PR whose body says `Closes #<n>`. Don't bundle several tickets into one PR, and don't commit to `main` directly.
- **Test-first** (`/tdd`): write a failing test at the ticket's seam, make it pass, then refactor. The API seam is HTTP through the app factory against the local test Postgres; the dashboard seam is Playwright E2E. Test behavior, not internals.
- **Done means** every acceptance criterion is checked, the tests pass, and lint and typecheck pass for every workspace the ticket touched. If a criterion turns out to be wrong or impossible, say so in the PR and on the ticket instead of silently skipping it.
- **Keep the docs true.** When a ticket adds commands, env vars or conventions, update the relevant `CLAUDE.md` in the same PR. When it settles a domain term or a hard-to-reverse decision, update `GLOSSARY.md` or add an ADR.
- **Scope creep becomes a new ticket.** Work found along the way that isn't in the ticket becomes a new issue linked to the parent spec, not extra changes in the current PR.

## Agents

Tickets are built by two project agents (`.claude/agents/`), each on Opus 5.5 at medium effort, in its own git worktree, one ticket at a time, ending in a PR written in Spanish with every acceptance criterion checked:

- **`api-developer`** takes every ticket labelled `api`.
- **`dashboard-developer`** takes every ticket labelled `dashboard`.

To build tickets, dispatch them through the `work-tickets` skill (`/work-tickets`, or `/work-tickets 4 14`) rather than implementing them in the main session. Both agents follow the `ticket-workflow` skill. Change it there, not in the agent definitions.
